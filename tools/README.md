# tools/

Standalone apps and one-off scripts built on top of the core `dog_brain_toolkit`
pipeline (`rsa_utils.py`, `searchlight.py`, `scheduler/`, `rsa_model_builder.py`,
`viz/`, etc.). Everything here is a *consumer* of the core toolkit — nothing in
the core toolkit imports from `tools/`.

Each script still lives directly in `tools/` (no subpackage) and adds both its
own folder and the repo root to `sys.path` at import time, so it can do a plain
`import rsa_utils`, `from scheduler.paths import ...`, `from viz import ...`, or
`import rsa_model_builder` exactly as it did when it lived at the repo root.
Run every script with the full Anaconda interpreter path from the repo root
(see `CLAUDE.md`), e.g.:

```powershell
& "C:\ProgramData\anaconda3\python.exe" tools\pipeline_dashboard.py
```

## Tools

| Tool | What it is |
|---|---|
| [`dashboard.py`](dashboard.py) | Unified entry point — one Flask server (port 8050) that mounts the Brain Viewer, RSA Model Builder, Scheduler, and Planner sub-apps under one URL with a tabbed landing page. Useful for sharing everything through a single tunnel. |
| [`pipeline_dashboard.py`](pipeline_dashboard.py) | Browser dashboard (Dash, port 8060) showing how far each RSA model has progressed through pipeline steps 0–10, by checking output files on disk. Editable run parameters, on-demand checks, per-parameter-set result cache. The **dis_method** (dropdown: pearson/kendall/euclidean/mahalanobis/correlation), **mah_fold**, and **rsa_model** menus are driven by the central `rsa_models/_models.csv` manifest — the rsa_model list shows **only** models in that manifest. `mahalanobis` is the special case that uses **mah_fold**: it filters the model list to the selected fold's models (and enables the fold dropdown); any other distance method drops the fold filter, greys out mah_fold, and offers every manifest model. The selected model's **why** note is shown. Reuses the probe logic in `pipeline_console.py`. Docs: [`../docs/pipeline_dashboard.md`](../docs/pipeline_dashboard.md). |
| [`pipeline_console.py`](pipeline_console.py) | Terminal version of the same progress probe — read-only, interactive menu or a non-interactive `--report` mode for scripting. Docs: [`../docs/pipeline_console.md`](../docs/pipeline_console.md). |
| [`hypothesis_explorer.py`](hypothesis_explorer.py) | Standalone Dash app (port 8055): a row of self-contained **model cards** (no hypothesis tree). Each card is one RSA model, picked in **two visual steps** rather than from a four-dropdown cascade. The analysis is still organised as `distance method → (Mahalanobis fold) → model → grouping`, but that is four menus of jargon in front of a question with two halves — *which stimulus pairs am I comparing* and *which hypothesis am I testing* — so the card asks those two, as pictures. **① How the stimuli are grouped**: one tile per (distance method, fold, grouping) the dataset offers, each drawn as **that grouping's own stimulus grid** — the design's two levels of categorisation, one row of icons per **agent block** (🐕 Dog-shown / 🧑 Human-shown) and one icon per **category** inside it (🤩 positive anticipation, 😀 happiness, 😠 anger, 😨 fear, 😐 neutral). The boxes carry the meaning: one box round everything is *pooled*, a box per row is *within*, two boxes joined by ⇅ is *cross* (only the pairs that bridge them), a lit row over a dimmed one is *Dog only* / *Human only*; the method and fold ride along as a small badge. Rows and columns are read off a model's own matrix, so another dataset draws *its* grid. **② Which hypothesis**: a gallery of the models available under that grouping, each tile showing the model's **own dissimilarity matrix** as a thumbnail plus its name and an ⓘ whose tooltip is the `why` column of `_models.csv`. The steps are shown **one at a time** — a fresh card opens ① alone, answering it swaps to ②, and answering that collapses both into a breadcrumb (`◧ grouping · method` · `▦ model`), so a card only spends screen space on choices that are still open; click either chip to reopen its step. Stem + grouping resolve to a concrete `{stem}__{grouping}` model (or a suffix-less model when that is the only file, e.g. `agent-species-id`), and the three cascade values are mirrored into hidden inputs so everything downstream reads them as before. The whole cascade and each model's **why** note come from the dataset's central [`rsa_models/_models.csv`](../tools/models_manifest.py) manifest (built by `build_models_manifest.py`), read from `{data folder}/{dataset}/rsa_models/` with **both taken from the top bar** — point the app at another project and it reads that project's manifest and model CSVs; the resolved manifest path is printed in the status line beside **Models**. When it is absent the card falls back to **scanning the `rsa_models` folder(s)** and offering every valid `__{grouping}` model under one synthetic method. It searches both the active results root and the pipeline data disk (`{datafolder}\{dataset}\rsa_models`). Each card is **one species** (its own **column** — model 1 → column 1, model 2 → column 2, …): the **Species** control picks **Dog** or **Human** and the card draws that species' results map as a 2D atlas slice (put Dog and Human side by side in two cards). **Which** map is drawn and **in which palette** are asked *on the picture*, by two floating switches in the slice's bottom corners — the way a map app puts its layer switcher in a corner rather than in a settings panel. Bottom-left is a three-segment **map-type** switch (`x̄` group average · `Z` z-map · `◉` cluster-corrected, defaulting to the group mean); bottom-right is the **colour palette**, collapsed to a swatch of the palette in use and opening on hover (or keyboard focus) into the full list, each entry drawn as itself rather than named. Axis / slice / z-threshold / an optional **max** (scale ceiling) stay per-card controls under the brain. The colormap defaults to **Hot**: voxels below the threshold render transparent (alpha=0), everything at/above rides the hot scale. **Next to the brain** the card draws a **histogram of that map's values inside the search mask** — only the voxels the searchlight visited, read from the ROI/mask file itself (dog masks from `Atlas/Dog/Nitzsche/`, human ones from `{dataset}/ROI/{specie}/`, tried against both the active data folder and the pipeline disk; a mask on a different grid is nearest-neighbour resampled onto the map's and the x-axis label says so, since results and mask are supposed to share one grid). It shares the brain view's height and the card's colormap: bars below the range slider's low handle are grey — exactly the voxels the slice draws transparent — and bars at/above it are coloured on the same `[low, high]` scale, with a bin boundary forced onto the low handle so the coloured bars sum to the reported supra-threshold count; both handles are marked as vertical lines and counts are on a **log** y-axis (a statistical map is overwhelmingly near-zero voxels). Toggle **📊 histogram** off to give the slice the full card width; the note under the slider reports `supra-threshold / in-mask` voxels. **Scroll the mouse wheel over a slice** to step through it one slice per notch (wheel up = higher slice index; the page itself does not scroll while the pointer is over the brain), and **click a slice to plant a crosshair**: the strip under the brain then reads out that voxel the way any MR viewer does — **voxel index**, **world (mm) coordinate** and the map's **intensity** there (values below the card's low threshold are still reported, flagged as *not painted*, since they are transparent rather than absent). The crosshair is held as a *voxel*, so it survives an axis switch, and its out-of-plane coordinate always follows the slice on screen — scroll and the read-out sweeps the same in-plane column, giving the value profile through a cluster. For **Z-map** / **Cluster-corrected** the threshold range defaults to **`[3.1, the map's own maximum]`** (recomputed on every map-type / model / grouping / species / source change, with the slider's upper limit growing past 8 when a map reaches further), so the palette spends its full range on the data instead of on unreached headroom; **Group average** keeps the fixed -1..1 scale. Toggle **🔗 sync** to mirror the view (slice, axis, threshold, max, colormap **and the crosshair**) across all *other synced cards of the same species* — move the slice on one and the matching-species cards follow, scales included, and click a voxel on one and every synced card of that species plants the crosshair on the **same voxel**, each reading out its *own* map's value there (same-species maps share one voxel grid, which is what makes the index transferable); Dog and Human sync independently. The card also shows the model's **dissimilarity matrix** (RSA Model Builder view); toggle **show matrix** off to hide it. **Beside the matrix** sits the **model-comparison bar plot**, the transpose of the brain view: where the slice asks *"where does this model fit?"*, the bars ask *"at this voxel, how do all the models compare?"* — one bar per model sampled at the crosshair, kept in **menu order** rather than sorted (a sorted plot would reshuffle every time the crosshair moves), with the card's own model in the accent colour and its low threshold marked. **Group average** maps carry **±SEM** error bars, from the `_std.nii.gz` map beside each mean over `sqrt(n)` with *n* = `len(file_list)` in the `_mean.json` sidecar (note the pipeline writes that std with ddof=0 and *n* counts averaged **maps** — participant runs, not participants); z-maps have no std twin, so no error bars. A scope menu picks who takes part: the card's method/fold + grouping (one bar per hypothesis — the only fully controlled comparison), that whole method/fold, or every model of every distance method. It is computed **on demand** via **📶 Compare**, never on a slider drag, since a scope can be dozens of maps on a network disk; the top-bar **Model bars** menu chooses how they are read — *On request* opens each map and reads **only the crosshair voxel** through nibabel's array proxy (the volume never enters memory, nothing is held between clicks), *Preloaded* loads the scope once so later samples come from RAM and the plot **follows the crosshair live**, reporting the MB held (**🧹 Free** drops them, as does switching mode or reloading). Measured on EmoC/Human — 13 models, 2 mm MNI, over `P:` — ~18 s per Compare on request vs ~18 s once and then instant for ~90 MB held. Toggle **📶 model bars** off to give the matrix the full card width. A per-card status dot flags whether computed results exist (dog / human / both / none). Maps can be read from **either** source: **Drive (current-results)** flat mirror, or **Raw (results/RSA)** nested pipeline output (`.../results/RSA/{glm_model}/{model}/mean/`, same paths `pipeline_dashboard.py` probes) — switch via the *Result source* menu; it auto-seeds the data folder. Use **➕ Add model** / per-card ✕ remove (up to 6 slots), and an **✏️ Edit** toggle: while on, drag a card's header to **reorder** it (cards are not resizable; a **Gap** box sets spacing and **Reset order** restores the default). Brain-view height is adjustable; the source mode / data folder / dataset / view height / model-bar read mode / card layout are saved to `~/.rsa_hypothesis_explorer_settings.json`, and each card's own selections (grouping tile, hypothesis, species, map type, axis, colormap, max, sync, histogram + matrix + model-bar show/hide, bar scope, on/off) are kept by Dash local persistence, so the cards come back next launch. **Updating is tiered so the app stays responsive over a network disk.** Only the choices that change *which file is read* — grouping tile, hypothesis, species, map type — wait on the top-bar **Auto-update** toggle; with it off a card shows a `⏸ change pending` note until you press either the card's own **🔄** button in its header (that card only) or the top bar's **🔄 Update now** (every enabled card). Everything that merely redraws what is already in RAM — slice, wheel scroll, axis, both threshold sliders, colormap, crosshair, view height, show/hide toggles — is always live, and each redraw rebuilds only the panels the change can affect (slice/axis/crosshair → brain only; threshold/colormap → brain + histogram; model → everything). Volumes are cached **by resolved file path** rather than by the selection behind it, so moving a threshold handle no longer re-reads the map (a cluster-corrected map carries the threshold in its file name and correctly resolves to a different file); model matrices are cached on the CSV's mtime, mask-restricted value arrays on the map's path, and raw-layout directory listings on the folder — all dropped together by **Reload results**. The app also **narrates itself to the terminal** (which card re-rendered and what triggered it, files read and how long they took, skipped renders, model-bar scans, cache drops) while Werkzeug's one-line-per-request access log is muted; `--verbose` adds cache hits and directory listings, `--quiet` logs warnings only, `--http-log` restores the access log. |
| [`models_manifest.py`](models_manifest.py) | Shared reader for the central `rsa_models/_models.csv` manifest — the single source of truth for **which models exist, which distance method and Mahalanobis fold each belongs to, which groupings each offers, and its `why` note**. Resolves the manifest from the caller's own `{datafolder}/{dataset}/rsa_models/` (then the pipeline data disk), so nothing here is project-specific. `dis_method` is the outermost key; `uses_fold()` says whether the fold level is a real choice (mahalanobis only), and `dis_index()` returns the dis-method → fold → stem → grouping structure the dashboards' menus are built from, always including a pooled `FOLD_ANY` entry per method for callers that skip the fold level. Both `pipeline_dashboard.py` and `hypothesis_explorer.py` read models through it (method/fold lists, model/grouping index, concrete-name resolution incl. suffix-less models, `why` lookup), so models are added/edited/re-grouped in **one file**. Tolerant of a missing/stale manifest (callers fall back to scanning the folder). |
| [`build_models_manifest.py`](build_models_manifest.py) | (Re)builds `rsa_models/_models.csv` from the two upstream battery manifests: the **stim-wise** `model_manifest_EmoC_RSA_model_battery.csv` (`why` ← its `why_test`, groupings ← `scope`) and the **run-wise** `_MODEL_BATTERY_MANIFEST.csv` (`why` ← `description` minus the grouping clause, groupings ← `grouping`). One row per model family × fold. Run it whenever either upstream manifest changes. |
| [`build_rsa_models.py`](build_rsa_models.py) | Generates the full factorial battery of EmoC RSA model CSVs (41 models) ready to feed into `searchlight.py` / the scheduler. Docs: [`../docs/RSA_model_battery_plan.md`](../docs/RSA_model_battery_plan.md). |
| [`build_all_categories_groupings.py`](build_all_categories_groupings.py) | Derives agent-species grouping variants (`__collapse`, `__cross`, `__dog`, `__hum`) of the hand-built `all-categories_{categorical,bipolar,emotionality}` models. Keeps the source 10×10 values and only NaN-masks the excluded condition pairs, reusing `build_rsa_models`' grouping predicates. Writes 12 CSVs next to the sources in `{datafolder}/EmoC/rsa_models/`. |
| [`set_live.py`](set_live.py) | Writes `docs/live.json` so the GitHub Pages landing page points at the current laptop tunnel URL (cloudflared/ngrok). Run once per session after starting the tunnel, then commit & push `docs/live.json`. |
| [`make_qr.py`](make_qr.py) | Generates a printable QR code (`docs/qr.png`) encoding the stable GitHub Pages landing URL. |
| [`create_package.py`](create_package.py) | Builds a self-contained `.zip` for **one participant × many RSA models** so the compute-heavy steps **1, 2, 4 run on a Colab GPU**. Supports both `--dis_method mahalanobis` (stim-wise, 45 category pairs) and `--dis_method correlation` (run-wise, 780 per-stimulus pairs). Bundles just the needed GLM betas, mask, model CSVs, config, the GPU code and a Colab notebook, plus a `manifest.json`. Checks whether the step-1 pairwise maps already exist on disk and, if so, bundles them so Colab skips step 1. `--all` expands to every model of the chosen `dis_method` in `rsa_models/_models.csv` (`--all-stim-wise` is the mahalanobis alias), via [`models_manifest.py`](models_manifest.py). See [`colab_gpu/README.md`](colab_gpu/README.md). |
| [`create_group_package.py`](create_group_package.py) | Builds the **group** counterpart of `create_package.py`: a package for RSA steps **3, 5, 6, 7** (group mean/std, `reps_group` group permutations, the voxelwise null distribution, and the z maps). It carries **no imaging data except the mask** — a few tens of kB — because the group steps start from the per-participant maps a Colab run has already written to Drive as `result_<model>_<specie>-sub-NN.zip`, and read them straight out of those zips. Records the participant list (from the config), `reps`/`reps_group`, `min_percentage_available` and the workstation `datafolder`, so the logs written on Colab carry workstation paths exactly like `rsa_utils`' own. Same `--models` / `--all` / `--all-stim-wise` selection rules as `create_package.py`. See [`colab_gpu/README.md`](colab_gpu/README.md). |
| [`unpack_results.py`](unpack_results.py) | Merges the `result_*.zip` files a Colab run writes (step-1 maps, per-model step-2/step-4 maps, and the group step-3/5/6/7 outputs) back onto the pipeline data disk. Extracts `.nii.gz` plus the sidecars the pipeline itself writes (`.json`, `.txt`, `.npy`) — step 3's `*_mean.json` is read back by `calculate_group_model_similarity_map` to decide whether the map must be recomputed, so dropping it would leave a merged run subtly different from a local one. Arc-paths are already pipeline-relative, so it's a validated merge (with `--dry-run` / `--replace` guards); afterwards `searchlight.py` steps 3–10 run as if the maps were computed locally. **Built to be restarted:** it decides "is this zip already unpacked?" with **one directory listing per folder**, cached run-wide and shared across zips, instead of one `os.path.exists` per member — on `P:` a single `scandir` returns 1560 names *and sizes* in 1.3 s where 1560 `exists` calls cost 87 s (~56 ms per round-trip). A zip that is fully present is reported complete and skipped without touching a single output path. Sizes come free with the listing, so a file left truncated by a killed run is detected and rewritten rather than skipped forever (`--no-verify-size` restores existence-only); new files go to a `.part` temp + atomic rename, so interrupting it cannot create a truncated map. Listings and copies run on a thread pool (`--workers`, default 16). |
| [`check_space.py`](check_space.py) | Pre-flight check that a dataset's beta maps all sit on the **same voxel grid** as the searchlight mask — same shape *and* same affine. The pipeline combines images by array index, so a grid mismatch produces results that look plausible but are anatomically meaningless; matching shapes alone prove nothing (FSL `regstandard_yn 1` only *estimates* the transform, leaving `stats/pe*.nii.gz` in scanner-native space, one grid per run). Reports per run whether it reads a **step-0.5 aligned** map or is still falling back to raw FEAT output — the same precedence `rsa_utils.resolve_beta_map()` applies — then prints per-participant displacement vs the mask and the spread across that participant's own runs. Exits non-zero on any mismatch, so it can gate a scheduler run. Same check `rsa_utils.check_same_space()` enforces inside steps 1–3. |
| [`make_mask.py`](make_mask.py) | Puts a dataset's searchlight mask on the **same grid the step-0.5 beta maps landed on**, reading the target grid from a `beta_manifest.json` (or `--reference`). Copies the source mask when it is already on that grid, otherwise resamples nearest-neighbour and re-binarises, then verifies the result with `check_same_space` before writing to `{dataset}/ROI/{specie}/{mask_type}.nii.gz` (backing up any existing mask to `*_pre-alignment.nii.gz`). Defaults to `Atlas/Hum/MNI/b_greyMatter2mmB.nii.gz` for humans and the Nitzsche equivalent for dogs, and warns about case-variant filenames, which Windows resolves and Linux does not. Run it after step 0.5 and before step 1. |
| [`colab_gpu/`](colab_gpu/README.md) | The GPU subsystem, in two halves that chain. **Per participant** — PyTorch reimplementation of RSA steps 1/2/4 (`gpu_rsa.py`) with its orchestrator/notebook (`run_colab.py`, `colab_rsa.ipynb`). **Group** — steps 3/5/6/7 (`gpu_group.py`, `run_colab_group.py`, `colab_rsa_group.ipynb`), whose input is the *output folder* of the first half: it reads the per-participant maps out of the `result_*.zip` files already on Drive, so nothing round-trips through the workstation in between. Step 5's `reps_group × n_participants` NIfTI loads collapse to one read of each map plus an index-gather. Both halves have a CPU-vs-GPU fidelity harness (`validate_gpu.py`, `validate_group.py`, validated to ~1e-12). |
| [`schedule_steps.py`](schedule_steps.py) | Queues an **arbitrary, possibly non-contiguous** set of pipeline steps for many RSA models at once — the case `schedule_rsa.py` cannot express, since it only takes a contiguous `--start_step .. --target_step` range. Builds the full graph with the tested `build_job_graph`, then prunes it to `--steps` (e.g. `3,5-10`) and rewires dependencies: a dep on a step you did not ask for is dropped, and any job left with no in-set dep starts `pending` instead of `waiting`. **A pruned step is therefore assumed already complete on disk** — prune only steps you know have run. Models come from `rsa_models/_models.csv`, filtered by `--dis_method` and expanded over each row's `groupings_possible` into `{model}__{grouping}`; `--rsa_model` targets a single one. Always creates jobs with `verbose=True`. Use `--dry_run` first: the default (all mahalanobis models × both species × 7 steps) is 700 files on the network disk. |
| [`glm_designer.py`](glm_designer.py) | Browser app (Dash, port 8061) — a simplified, experiment-specific clone of **FSL FEAT's Stats tab**. You supply a working `.fsf`; it copies that design and replaces **only** its EV/contrast model, so input paths, TR, volumes, smoothing, registration and thresholds come across untouched (they are rewritten per subject/run later by `rsa_utils.calculate_beta_maps` anyway). **EVs are auto-populated from the config's `stim_types`** — pick species (D/H) and model (`basic`, `basic-block`, …) and the conditions appear in order, with the colour/label chips from `model_dict`. **Contrasts** are a FEAT-style numeric grid (one row per contrast, one cell per condition); **Identity** seeds one per condition and **Mean by `label` / `specie_shown` / `run_label` / `partition`** builds one averaging contrast per group straight from `model_dict` — the thing you do not want to type by hand for 40 conditions. Per-EV settings (shape, convolution, temporal filtering, temporal derivative) are lifted from the template's EV 1, and the output is written in `con_mode orig` with the *real* contrast vectors derived (derivative columns zeroed), so `feat` and the FEAT GUI both load it. Preview before saving; F-tests are not generated and the app says so when the template has them. Engine: [`fsf_design.py`](fsf_design.py). |
| [`fsf_design.py`](fsf_design.py) | Dash-free engine behind `glm_designer.py`, usable as a library or in scripts: parses a FEAT `.fsf` into comment-headed blocks, classifies each as EV / contrast / keep, and regenerates the EV and contrast sections in place. Everything else is preserved byte-for-byte apart from the seven counters that must follow the model (`evs_orig`, `evs_real`, `evs_vox`, `ncon_orig`, `ncon_real`, `nftests_*`). Also reads a template back out (`template_summary`, `template_contrasts`, `ev_options_from_template`) and offers the contrast builders (`identity_contrasts`, `mean_contrasts_by_group`) and the pipeline's timing-file convention (`custom_files_for` → `{dir}/{condition}.txt`). Rebuilding from its own output is byte-stable. |
| [`queue_scan.py`](queue_scan.py) | Fast state scan of the job queue as a (rsa_model × step × species) matrix. Does **one `listdir` per state folder** (~13 s for ~5600 files) and resolves every job id from that in-memory index, including `__dup{N}` siblings — the obvious alternative of globbing per job id is 500+ round trips against the network mount and reliably exceeds a two-minute timeout. Applies the same state precedence as `job_status.py` (`running > pending > waiting > completed > failed`), so a fresh duplicate outranks a stale completed record. `--summary` for counts, `--missing_only` to list absent jobs, `--rsa_model` for one model. Prefer this over `job_status.py` whenever more than a couple of models are involved. |

## Adding a new tool

New standalone tools/scripts belong in this folder, not the repo root. When you
add one:

1. Put the script (and any folder it creates for its own data/cache, if that
   data isn't already going to the shared network disk) inside `tools/`.
2. Add both the repo root and `tools/` itself to `sys.path` at the top, following
   the pattern already used by the scripts above, so imports of core modules
   (`rsa_utils`, `scheduler.*`, `viz.*`, `rsa_model_builder`) keep resolving.
3. Add a row for it to the table above.
